Code examples marked "verbatim" were extracted from the cited pages through a fetch tool that summarises; check them against the source before quoting them in print. ## 1. Equation-Based Languages: What Each Expresses and Where It Stops

### Takeaway
The equation-based languages divide into three kinds: line-oriented solver inputs (XPPAUT), declarative exchange formats with units and hierarchy but narrow mathematics (CellML, SBML, NeuroML/LEMS, NESTML), and embedded symbolic systems that keep equations as transformable expressions (ModelingToolkit/Catalyst, Brian 2, Dedalus, UFL, Devito). Only ModelingToolkit with Catalyst covers ODE, DAE, SDE, jumps, events and PDE declarations in one symbolic representation, and even it has no notion of an action, a quantum state space or a rewriting rule.

### Cited Findings

**XPPAUT `.ode` files**
- A `.ode` file is plain line-oriented text: ODEs as `x'=-x+sin(t)` or `dw/dt=...`, maps as `z(t+1)=z*(4-z)`, parameters by `par`, fixed constants by `number`, initial data by `init` or `x(0)=expr`, plotted quantities by `aux`, user functions `f(x,y)=formula`, and `done` at the end — [XPP ODE file reference](https://sites.pitt.edu/~phase/bard/bardware/xpp/help/xppodes.html)
- One file covers delay equations (`delay(x,2)` in a right-hand side, with a history given by `x(0)=expr` in `t`), Volterra integral equations (`int{exp(-t)#x}`), DAEs (`0=` and `solve`), boundary conditions (`bdry`), and indexed arrays (`name[j1..j2]`) — [XPP ODE file reference](https://sites.pitt.edu/~phase/bard/bardware/xpp/help/xppodes.html)
- Noise and jumps are declarations in the same file: `wiener name1, name2` declares Wiener increments "with standard deviation sqrt(dt)", and `markov name nstates` followed by a matrix of transition rates declares a finite-state Markov variable — [XPP ODE file reference](https://sites.pitt.edu/~phase/bard/bardware/xpp/help/xppodes.html)
- Events are `global sign condition {name=form;...}`: when the condition crosses zero in the stated direction the listed variables are reset — [XPP ODE file reference](https://sites.pitt.edu/~phase/bard/bardware/xpp/help/xppodes.html)
- The reference page has nothing on units, PDEs or modules; the only inclusion mechanism it describes is called obsolete — [XPP ODE file reference](https://sites.pitt.edu/~phase/bard/bardware/xpp/help/xppodes.html)
- Example (assembled from fragments of the page): `par a=1` / `x'=-x+a*sin(t)` / `y'=x-y` / `init x=0,y=1` / `done` — [XPP ODE file reference](https://sites.pitt.edu/~phase/bard/bardware/xpp/help/xppodes.html)
- Licence: GNU GPL version 2 **[copyleft]** — [xppaut LICENSE](https://github.com/Ermentrout/xppaut/blob/HEAD/LICENSE)

**Modelica**
- The specification's development version is 3.8-dev; the latest released tag is v3.7 — [Modelica specification, ch. 8](https://specification.modelica.org/master/equations.html); [ModelicaSpecification releases](https://github.com/modelica/ModelicaSpecification/releases/latest)
- The specification text is licensed CC BY-SA 4.0 **[copyleft for the text]** — [ModelicaSpecification LICENSE.md](https://github.com/modelica/ModelicaSpecification/blob/HEAD/LICENSE.md)
- Events are written as when-equations whose body is active "only at the instant when the scalar expression or any of the elements of the vector expression becomes true"; `reinit` "can only be used in a when-equation body"; `pre()` gives the value before the event. The specification's bouncing ball: `der(h) = v; der(v) = if flying then -g else 0; flying = not (h <= 0 and v <= 0); when h < 0 then reinit(v, -e * pre(v)); end when` — [Modelica specification, ch. 8](https://specification.modelica.org/master/equations.html)
- Relations such as `x > 2` generate state events located by root finding; `time >= ...` gives time events known in advance; `noEvent(...)` takes a relation literally; `elsewhen` gives priority among simultaneous conditions; when-equations cannot be nested; simultaneity of events is not guaranteed and must be modelled explicitly — [Modelica specification, ch. 8](https://specification.modelica.org/master/equations.html)
- Noise is a library matter, not a language construct: a 2014 paper introduced a library for pseudo-random noise because Modelica had no convenient way to specify noise; its basic blocks entered the Modelica Standard Library 3.2.2 as `Modelica.Blocks.Noise` (uniform, normal, truncated normal, band-limited white noise, a global seed block); the DLR AdvancedNoise library adds event-free generators and spectral shaping — [Klöckner et al. 2014](https://ep.liu.se/ecp/096/087/ecp14096087.pdf); [Modelica.Blocks.Noise](https://doc.modelica.org/om/Modelica.Blocks.Noise.html); [AdvancedNoise](https://github.com/DLR-SR/AdvancedNoise)

**ModelingToolkit.jl and Catalyst.jl**
- ModelingToolkit's documentation is at v11.46.1 ("ModelingToolkit version 11 just released"); the repository's latest release tag is `ModelingToolkitBase-v1.80.0`; licence MIT — [MTK docs](https://docs.sciml.ai/ModelingToolkit/stable/); [MTK releases](https://github.com/SciML/ModelingToolkit.jl/releases/latest); [MTK LICENSE.md](https://github.com/SciML/ModelingToolkit.jl/blob/HEAD/LICENSE.md)
- It names ODEs (`System`), SDEs (`SDESystem`), jump systems (`JumpSystem`), nonlinear systems, optimisation systems, PDEs (`PDESystem`, discretised by MethodOfLines.jl or solved by NeuralPDE.jl), continuous-time Markov chains and reactions through Catalyst, and nonlinear optimal control; it describes causal and acausal modelling, automated transformation, simplification and composition, index reduction of DAEs, alias elimination and tearing, use of the whole Symbolics.jl computer algebra system, and import from SBML, CellML and BioNetGen — [MTK docs](https://docs.sciml.ai/ModelingToolkit/stable/)
- Reference paper: Ma, Gowda, Anantharaman, Laughman, Shah, Rackauckas, "ModelingToolkit: A Composable Graph Transformation System For Equation-Based Modeling", arXiv:2103.05244 — [MTK docs](https://docs.sciml.ai/ModelingToolkit/stable/)
- Events are symbolic: `System` and `SDESystem` accept `continuous_events` (root-found zero crossings) and `discrete_events` (checked after each step); `JumpSystem` only discrete ones. Bouncing ball (verbatim): `@variables x(t)=1 v(t)=0` / `root_eqs = [x ~ 0]` / `affect = [v ~ -Pre(v)]` / `@mtkcompile ball = System([D(x) ~ v, D(v) ~ -9.8], t; continuous_events = root_eqs => affect)`. `Pre(x)` is the value before the event; a parameter may be changed only if declared in `discrete_parameters`; a single event cannot mix changes to variables and to parameters; imperative affects are experimental — [MTK events](https://docs.sciml.ai/ModelingToolkit/stable/basics/Events/)
- Units are metadata, `@variables x(t) [unit = u"m"]` (DynamicQuantities), validated automatically when a system is built; there is no automatic conversion (kJ against J fails), no unitful literals inside functions, and no affine or angular-degree units — [MTK unit validation](https://docs.sciml.ai/ModelingToolkit/stable/basics/Validation/)
- Catalyst is at v17.0.1, MIT. Its DSL (verbatim): `@reaction_network begin (p,d), 0 <--> X end`. One `ReactionSystem` yields ODE, steady-state, SDE (chemical Langevin), jump (stochastic chemical kinetics) and hybrid simulations; Jacobians, sparsity, dependency graphs, linkage classes, deficiencies, reversibility, steady states with stability and bifurcation diagrams are derived; reactions may be coupled with differential equations, Brownian noise (`@brownians`) and Poisson processes (`@poissonians`); composition is by `@network_component`, `compose` and `extend`; discrete-space (lattice) reaction models are supported; SBML and BioNetGen `.net` files are imported — [Catalyst docs](https://docs.sciml.ai/Catalyst/stable/); [Catalyst LICENSE.md](https://github.com/SciML/Catalyst.jl/blob/HEAD/LICENSE.md)

**Brian 2 equation strings**
- Equations are strings parsed by Brian (not arbitrary Python), each line of the form `dx/dt = f : unit (flags)`, e.g. `"dv/dt = -v / tau : 1"`. The unit after the colon must be an SI base unit ("one must write `volt`, not `mV`") and describes the variable, not its derivative — [Brian 2 equations](https://brian2.readthedocs.io/en/stable/user/equations.html)
- Noise is the symbol `xi` in an equation, with suffixes (`xi_1`, `xi_inh`) for independent sources; the page's example `sigma/tau**.5*xi : volt` shows its scaling; noise is independent across neurons — [Brian 2 equations](https://brian2.readthedocs.io/en/stable/user/equations.html)
- Flags after the unit qualify a variable: `event-driven`, `unless refractory`, `constant`, `constant over dt`, `shared`, `linked` — [Brian 2 equations](https://brian2.readthedocs.io/en/stable/user/equations.html)
- The numerical method is chosen apart from the equations by a `method` keyword (`exact`, `exponential_euler`, `euler`, `rk2`, `rk4`, `heun`, `milstein`, GSL variants), or automatically; `euler` is listed for additive noise, `milstein` for diagonal multiplicative noise, and `heun` for "Stratonovich" SDEs with non-diagonal multiplicative noise — [Brian 2 numerical integration](https://brian2.readthedocs.io/en/stable/user/numerical_integration.html)
- Current release 2.11.0; licence CeCILL 2.1 **[copyleft, GPL-compatible]** — [Brian2 on PyPI](https://pypi.org/project/Brian2/); [brian2 LICENSE](https://github.com/brian-team/brian2/blob/HEAD/LICENSE)

**NESTML**
- A model is a block structure with typed physical quantities. From the shipped Izhikevich model (verbatim excerpt): `model izhikevich_neuron:` / `state:` `V_m mV = V_m_init` / `equations:` `V_m' = (0.04 * V_m * V_m / 1 mV + 5 * V_m + (140 - U_m) * 1 mV + ((I_e + I_stim) * 1 GOhm)) / 1 ms` / `parameters:` `V_th mV = 30 mV` / `input:` `input_spikes <- spike`, `I_stim pA <- continuous` / `output: spike` / `onReceive(input_spikes): V_m += unit_psp * get_weight(input_spikes, t)` / `update: integrate_odes()` / `onCondition(V_m >= V_th): V_m = c; U_m += d; emit_spike()` — [izhikevich_neuron.nestml](https://github.com/nest/nestml/blob/master/models/neurons/izhikevich_neuron.nestml)
- Events are `onCondition` blocks (threshold, reset, `emit_spike()`) and `onReceive` blocks for incoming spikes; the `update` block is imperative and calls `integrate_odes(...)` — [Modeling neurons in NESTML](https://nestml.readthedocs.io/en/latest/nestml_language/neurons_in_nestml.html)
- Latest release v9.0.1; licence GPL version 2 **[copyleft]** — [nestml releases](https://github.com/nest/nestml/releases/latest); [nestml LICENSE](https://github.com/nest/nestml/blob/HEAD/LICENSE)

**NeuroML 2 / LEMS**
- LEMS is "a language for specifying hierarchical models based on fundamental physical relationships"; a `ComponentType` declares parameters with a `dimension` attribute (voltage, time, capacitance), children, exposures and event ports, and a `Dynamics` element holding `StateVariable`, `TimeDerivative`, `OnStart`, `OnCondition`, `OnEntry`, `Regime`, `Transition`, `StateAssignment` and `EventOut`; values carry units inline (`-40mV`, `5ms`) — [LEMS in the NeuroML documentation](https://docs.neuroml.org/Userdocs/LEMS.html)
- Hybrid modes are `Regime` elements, one marked `initial="true"`, each with its own equations; an `OnCondition` test triggers a `Transition`. Verbatim: `<OnCondition test="v .gt. threshold"> <EventOut port="out" /> <Transition regime="refr" /> </OnCondition>` — [LEMS in the NeuroML documentation](https://docs.neuroml.org/Userdocs/LEMS.html)
- NeuroML 2's latest release tag is NMLv2.3.1, under LGPL version 3 **[weak copyleft]**; the reference interpreter jLEMS is v0.11.1 under MIT — [NeuroML2 releases](https://github.com/NeuroML/NeuroML2/releases/latest); [NeuroML2 LICENSE.lesser](https://github.com/NeuroML/NeuroML2/blob/HEAD/LICENSE.lesser); [jLEMS LICENSE](https://github.com/LEMS/jLEMS/blob/HEAD/LICENSE)

**CellML 2.0**
- CellML 2.0 is defined by a normative specification with an informative version beside it; governance of the specification moved to the CellML Specification Custodian Board with effect from 16 May 2026 — [CellML 2.0 specification page](https://www.cellml.org/specifications/cellml_2.0/)
- The reference library libCellML is at v0.7.2 under Apache 2.0 — [libcellml releases](https://github.com/cellml/libcellml/releases/latest); [libcellml LICENSE](https://github.com/cellml/libcellml/blob/HEAD/LICENSE)

**SBML and Antimony**
- The current core is SBML Level 3 Version 2 Release 2 (2019-03-29, DOI 10.1515/jib-2019-0021). Released packages: `comp` (hierarchical composition), `distrib` (values sampled from distributions), `fbc`, `groups`, `layout`, `multi` (multistate, multicomponent species and rules on them), `qual`, `render`, `spatial` (processes with a spatial component and their geometries); `arrays` and `dyn` remain drafts — [SBML specifications](https://sbml.org/documents/specifications/)
- Antimony is a text front end to SBML. Verbatim: `model example1` / `S1 -> S2; k1*S1` / `S1 = 10` / `S2 = 0` / `k1 = 0.1` / `end` — [Antimony reference](https://tellurium.readthedocs.io/en/latest/antimony.html)
- Antimony events: `at (x>5): y=3, x=r+2;`, with a delay `E1: at 2 after (x>5): ...`, and options `priority`, `t0`, `persistent`, `fromTrigger`; rate rules `X' = ...`; assignment rules `:=` — [Antimony reference](https://tellurium.readthedocs.io/en/latest/antimony.html)
- Antimony units are declared (`unit micromole = 10e-6 mole / liter;`) but "are for annotation only and do not affect the math"; derived units are not computed — [Antimony reference](https://tellurium.readthedocs.io/en/latest/antimony.html)
- Antimony modules take interface arguments (`model side_reaction(S, k1) ... end`), are instantiated by name (`A: side_reaction(S1, k4)`) and joined by `A.S is B.S`; modules are flattened in SBML unless `comp` is used — [Antimony reference](https://tellurium.readthedocs.io/en/latest/antimony.html)
- Antimony has distribution functions (`normal(mean, stddev)`, `uniform`, `poisson`, since v2.12) and uncertainty annotations, written to SBML `distrib`; a later definition of a symbol silently replaces an earlier one — [Antimony reference](https://tellurium.readthedocs.io/en/latest/antimony.html)
- Antimony v3.3.0 (PyPI 2026-10-28); its repository licence is a BSD-style three-clause text, while its PyPI metadata says "MIT" — [antimony LICENSE.txt](https://github.com/sys-bio/antimony/blob/HEAD/LICENSE.txt); contradicted by [antimony on PyPI](https://pypi.org/project/antimony/)

**PyDSTool**
- A system is specified by dictionaries of strings in "index-free" notation: model name and state variables (required), auxiliary variables, helper functions (`auxfns = {'P': ([], 'B*exp(A)')}`), parameters, domains, initial conditions, external inputs, user-defined events and algorithmic parameters; target languages are Python, C and ADMC++; a hybrid `Model` class handles discrete events in continuous-time systems — [PyDSTool functional specification](https://pydstool.github.io/PyDSTool/FunctionalSpec.html)
- The last release on PyPI is 0.91.0 of 2020-01-31, licence BSD; the licence file's copyright line ends in 2014 — [PyDSTool on PyPI](https://pypi.org/project/PyDSTool/); [pydstool LICENSE.txt](https://github.com/robclewley/pydstool/blob/HEAD/LICENSE.txt)

**Dedalus (v3)**
- Equations are strings parsed in a namespace of fields and operators. Verbatim: `problem = d3.IVP([u, tau1, tau2], namespace=locals())` / `problem.add_equation("dt(u) - u - (1 + 1j*b)*dx(dx(u)) + tau1*p1 + tau2*p2 = - (1 + 1j*c) * magsq_u * u")` — [Dedalus tutorial 3](https://dedalus-project.readthedocs.io/en/latest/notebooks/dedalus_tutorial_3.html)
- The form is constrained: "The left-hand side (LHS) of the equations must be first-order in temporal derivatives and linear in the problem variables"; the right-hand side "may contain nonlinear and time-dependent terms, but no temporal derivatives" (M·∂ₜX + L·X = F(X, t)). Four problem classes: `IVP`, `EVP`, `LBVP`, `NLBVP`. Boundary conditions need tau terms added explicitly as unknowns — [Dedalus tutorial 3](https://dedalus-project.readthedocs.io/en/latest/notebooks/dedalus_tutorial_3.html)
- v3.0.5 (PyPI 2026-01-31); GPL version 3 **[copyleft]** — [dedalus on PyPI](https://pypi.org/project/dedalus/); [dedalus LICENSE.txt](https://github.com/DedalusProject/dedalus/blob/HEAD/LICENSE.txt)

**FEniCS UFL**
- UFL is a Python-embedded language for variational forms and functionals, e.g. `a = inner(grad(u), grad(v))*dx`, with measures `dx`, `ds`, `dS`; the mesh and its subdomains are not known to UFL but to the surrounding environment — [UFL form language](https://fenics.readthedocs.io/projects/ufl/en/latest/manual/form_language.html)
- Derived automatically from a form: `derivative(F, w, u)` (Gateaux derivative; applied to a residual it gives the Jacobian), `adjoint(a)`, `action(a, w)`, `lhs(F)`/`rhs(F)`, `replace`, `energy_norm` — [UFL form language](https://fenics.readthedocs.io/projects/ufl/en/latest/manual/form_language.html)
- UFL "does not implement time in any particular way": there is no time derivative or time stepping in the language — [UFL form language](https://fenics.readthedocs.io/projects/ufl/en/latest/manual/form_language.html)
- Release 2026.2.0 (PyPI 2026-09-30); the repository's `COPYING` is the GNU GPL version 3 text **[copyleft; see Gaps for the LGPL question]** — [fenics-ufl on PyPI](https://pypi.org/project/fenics-ufl/); [ufl COPYING](https://github.com/FEniCS/ufl/blob/HEAD/COPYING)

**Devito**
- Devito is a Python package for optimised stencil computation (finite differences) from "high-level symbolic problem definitions"; it "builds on SymPy and employs automated code generation and just-in-time compilation" for CPUs, GPUs and clusters, primarily for wave propagation in seismic inversion; it lists "seamless support for boundary conditions and adjoint operators" — [Devito project page](https://www.devitoproject.org/)
- v4.8.23 (PyPI 2026-08-07); MIT — [devito on PyPI](https://pypi.org/project/devito/); [devito LICENSE.md](https://github.com/devitocodes/devito/blob/HEAD/LICENSE.md)

### Inferences
- The exchange formats (CellML, SBML core, LEMS) deliberately keep the mathematics narrow, ODEs with algebraic rules and events, to stay portable between simulators; every extension beyond that (distributions, space, rules) arrived as an optional package with thin tool support. A new language that wants several kinds of system in one notation cannot be a lowest common denominator of simulators and must define its own semantics.
- Units are handled in four distinct ways: absent (XPPAUT, PyDSTool, Dedalus, UFL), annotation only (Antimony), dimensional checking without conversion (ModelingToolkit, Brian 2 with base units), and dimensional typing with literals carrying units (NESTML, LEMS). NESTML's `1 mV`, `1 ms` literals inside equations and LEMS's `dimension` attribute are the closest precedents to units carried in the type.
- Dedalus's rule (left side linear and first order in time, right side explicit) shows a language exposing the numerical method's structure in its syntax; UFL shows the opposite, a language of space alone with time left to the host program. Neither separates the mathematical statement fully from the method.
- PyDSTool is effectively unmaintained (no release since January 2020); XPPAUT's format is stable and old. Both remain the reference for how much a terse line-oriented file can say (delays, Volterra terms, Markov variables and Wiener terms in one file), at the cost of no units, no composition and no symbolic access.

From prior knowledge (not verified in this session): CellML 2.0 has resets as its only event construct, requires units on every variable, and has no PDE, delay or stochastic construct.
- SBML's core event semantics (trigger, delay, priority, `persistent`) and the `delay` csymbol were not re-read from the specification; they are reflected here only through Antimony's syntax for them.
- Brian 2's page on thresholds and resets (`threshold='v > v_th'`, `reset='v = v_r'`, custom events) was not fetched; the equations page mentions reset statements only in passing.
- NESTML's documentation pages on units and on random functions returned 404; whether `random_normal` and similar functions are current in v9 is unverified.
- UFL is, from prior knowledge, distributed under LGPL-3.0-or-later (a `COPYING.LESSER` beside `COPYING`); only the GPL text was read in this session. Either way it is copyleft.

## 2. Hybrid and Event Systems: How Guards, Resets and Mode Changes Are Written

### Takeaway
Two traditions exist. The equation-based one (Modelica, ModelingToolkit, Antimony, XPPAUT, NESTML) attaches events to a single set of equations as condition–reset pairs; the automaton-based one (SpaceEx, CIF, LEMS regimes, Ptolemy II modal models, JANI) makes the mode a first-class location with its own flow, invariant, guards and assignments. No format surveyed types a mode change as a change of state space: all assume a fixed set of variables across modes.

### Cited Findings
- **Modelica:** guard = the condition of a `when`; reset = `reinit(v, expr)` with `pre(v)`; priority among simultaneous events by `elsewhen`; no nesting; the specification notes that events do not guarantee simultaneity — [Modelica specification, ch. 8](https://specification.modelica.org/master/equations.html)
- **ModelingToolkit:** guard = an equation whose zero crossing is root-found (`[x ~ 0]`), reset = equations in `Pre(·)` (`[v ~ -Pre(v)]`); separate affects for the negative edge (`affect_neg`); discrete events as conditions, preset times or periods — [MTK events](https://docs.sciml.ai/ModelingToolkit/stable/basics/Events/)
- **XPPAUT:** `global sign condition {resets}`, the sign giving the direction of crossing — [XPP ODE file reference](https://sites.pitt.edu/~phase/bard/bardware/xpp/help/xppodes.html)
- **Antimony/SBML:** `at (trigger): assignments`, with delay, priority, persistence and whether a trigger true at time 0 fires — [Antimony reference](https://tellurium.readthedocs.io/en/latest/antimony.html)
- **LEMS:** named `Regime`s with their own `TimeDerivative`s, `OnEntry` actions, and `OnCondition` → `Transition regime="..."` — [LEMS in the NeuroML documentation](https://docs.neuroml.org/Userdocs/LEMS.html)
- **SpaceEx (SX format, XML):** each location has an id, an invariant and a flow (a list of ODEs); each transition has an optional guard and an optional assignment; networks of components are flattened by SpaceEx's `sspaceex` tool before some parsers accept them — [SpaceExParser.jl methods](https://juliareach.github.io/SpaceExParser.jl/dev/lib/methods)
- The SX format "closely mirrors the mathematical definition of hybrid automata", which is why other tools are targeted from it — [SL2SX, HSCC 2016](https://cps-vo.org/sites/cps-vo.org/files/cpsvo_file_nodes/MinopoliF_HSCC16bpdf.pdf)
- In SpaceEx, components sharing a transition label fire together, and a variable must be declared uncontrolled in a component if another component's transition is to change it — [ECC 2013 paper on SpaceEx models](https://skoge.folk.ntnu.no/prost/proceedings/ecc-2013/data/papers/1270.pdf)
- SpaceEx's site states "All contents released under GPL v.3" **[copyleft]** — [SpaceEx](http://spaceex.imag.fr/)
- **HyST** (Bak, Bogomolov, Johnson, HSCC 2015, DOI 10.1145/2728606.2728630) translates SpaceEx models into the inputs of HyCreate, Flow* and dReach, because hybrid model checkers share roughly the same semantics but "drastically different model description languages"; it includes model transformation passes (e.g. pseudo-invariants). Licence LGPL version 3 **[weak copyleft]**; no tagged releases — [HyST record](https://research-explorer.ista.ac.at/record/1690); [hyst LICENSE](https://github.com/verivital/hyst/blob/HEAD/LICENSE)
- **CIF (Eclipse ESCET):** "a declarative modeling language for the specification of discrete event, timed, and hybrid systems as a collection of synchronizing automata", with tools for supervisory controller synthesis, simulation, verification and code generation; version v13.0 — [CIF](https://eclipse.dev/escet/cif/)
- CIF continuous variables are real-valued, default to 0.0, and their derivative can be used as a variable; they can be assigned on edges like discrete variables. An edge is written with a guard and an update, e.g. `edge when x >= 8 do x := 0, y := 0 goto Rest` — [CIF tutorial, continuous variables](https://eclipse.org/escet/cif/language-tutorial/time/continuous-variables.html); [ESCET course, module 5 exercises](https://eclipse.dev/escet/sbe-course/module5/exercises.html)
- ESCET's licence text is the MIT permission notice (copyright 2010, 2026 Contributors to the Eclipse Foundation) — [ESCET LICENSE.txt](https://gitlab.eclipse.org/eclipse/escet/escet/-/raw/develop/LICENSE.txt)
- **Ptolemy II:** hybrid systems are finite state machines nested hierarchically with continuous-time models; a state's refinement is active while the state is; each transition carries a guard and actions, which "can reset variables in the refinement of the destination state, or produce outputs"; "set" actions are distinct from "output" actions; refinements may themselves be FSMs, modal models or any composite actor with a compatible director; models are stored in MoML (XML) — [Lee, FSMs and modal models in Ptolemy II, EECS-2009-151](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2009/EECS-2009-151.pdf); [Ptolemy modal models](https://ptolemy.berkeley.edu/eecs20/hybrid/modal.html); [distributed hybrid systems in Ptolemy II](https://ptolemy.eecs.berkeley.edu/publications/papers/01/distributedHybrid/distributedHybrid.pdf)
- Ptolemy II's latest release tag is `rel-11-0-1`; its copyright notice (1995–2021, Regents of the University of California) is a permissive BSD-style grant — [ptII releases](https://github.com/icyphy/ptII/releases/latest); [ptII copyright.txt](https://github.com/icyphy/ptII/blob/HEAD/copyright.txt)
- **JANI:** a JSON model format (`jani-model`) for networks of quantitative automata with variables, plus a tool protocol; supported by ePMC, FIG, the Modest Toolset and Storm; designed for ease of implementation, generated by tools and "not designed to be human-writable"; it covers concurrency, probabilistic and real-time aspects "as well as continuous dynamics" — [JANI specification](https://jani-spec.org/); [Momba: JANI meets Python](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC7984561/); [Overview of Modest models and tools, arXiv:2203.09881](https://arxiv.org/pdf/2203.09881)

### Inferences
- Guards are written in three ways: as a Boolean becoming true (Modelica `when`, Antimony `at`), as a signed zero crossing (XPPAUT `global sign`, ModelingToolkit root equations with `affect_neg`), and as a guard region enabling an edge, with urgency a separate matter (SpaceEx, CIF, Ptolemy). A new language should state which it means, since "becomes true" and "is enabled" differ when a trajectory starts inside the guard.
- Resets are everywhere assignments to the same variables. None of the formats lets a mode have a different state space with a typed map between them (a ball that becomes two fragments, a rewrite that adds cells). Ptolemy's refinements with their own directors come nearest, but the map between refinements' states is an untyped list of set actions.
- The automaton formats are verification inputs (reachability), and so restrict flows (affine or polynomial) and exclude noise in the flow; the equation languages are simulation inputs and leave the semantics of simultaneous events to the tool. Modelica's `elsewhen` and Antimony's `priority` are the only explicit orderings found.

### Gaps
- No complete SpaceEx XML file was retrieved; the tag names (`component`, `location`, `invariant`, `flow`, `transition`, `guard`, `assignment`, `bind`) are known from the parser's documentation and prior knowledge only.
- A full CIF hybrid example (declaration `cont x der ...;`, `equation x' = ...`, urgency) could not be read: the tutorial page's body was truncated. CIF's stochastic distribution types (`dist`, sampling on edges) are from prior knowledge and unverified.
- JANI's list of model types (LTS, DTMC, CTMC, MDP, MA, TA, PTA, STA, HA, PHA, SHA) is from prior knowledge; the specification's front page did not list them.
- MoML's concrete element names for guards and actions were not retrieved.
- No source was found for any hybrid format in which a mode change alters the dimension or type of the state.

## 3. Stochastic Systems and Random Variables: How Noise Is Declared, and Whether Itô or Stratonovich Is Stated

### Takeaway
A random variable is declared in two unrelated ways: probabilistic programming languages name a draw from a distribution (`x ~ Normal(a, 1)`, `pyro.sample("x", dist)`) inside otherwise arbitrary code, while dynamical languages name a noise process inside an equation (`xi`, `wiener w`, `@brownians`). The interpretation of a stochastic integral is almost never part of the model: in DifferentialEquations.jl and Brian 2 it is a property of the solver chosen.

### Cited Findings
- **Stan** (v2.40; code BSD 3-clause, documentation CC-BY ND 4.0): a quantity's law is stated by a sampling statement, `y[t] ~ normal(mu[t], sigma);`, and noise in simulation by `normal_rng` in generated quantities — [Stan reference manual](https://mc-stan.org/docs/reference-manual/); [Stan user's guide, ODEs](https://mc-stan.org/docs/stan-users-guide/odes.html)
- Stan's dynamics are opaque user functions handed to solvers: `vector sho(real t, vector y, real theta) { ... return dydt; }` and `ode_rk45(sho, y0, t0, ts, theta)`; solvers rk45, bdf, adams, ckrk and an adjoint solver on CVODES; the solver must also give the gradient, by forward sensitivities (N·M extra states) or adjoints. The ODE chapter does not mention stochastic or delay differential equations or events; for discontinuities it advises integrating between them and restarting — [Stan user's guide, ODEs](https://mc-stan.org/docs/stan-users-guide/odes.html)
- **Pyro** (1.9.2, Apache 2.0) and **NumPyro** (0.22.0, Apache 2.0): `sample(name, fn, *args, obs=None, ...)` calls a stochastic function with effects that depend on its name and the enclosing inference context; `obs` conditions; also `param`, `plate` (conditional independence), `factor` (an arbitrary log-probability term) and `deterministic` — [Pyro primitives](https://docs.pyro.ai/en/stable/primitives.html); [pyro LICENSE.md](https://github.com/pyro-ppl/pyro/blob/HEAD/LICENSE.md); [numpyro releases](https://github.com/pyro-ppl/numpyro/releases/latest)
- **Turing.jl** (v0.49, MIT). Verbatim: `@model function mymodel()` / `a ~ Normal(0, 1)` / `x ~ Normal(a, 1)` / `end`. A `~` statement is an observation if the variable is an argument or is conditioned (`model() | (x = 1,)`), else an assumption; "arbitrary Julia code can be used" in the model; samplers SMC, PG, HMC, MH, Gibbs, NUTS — [Turing core functionality](https://turinglang.org/docs/core-functionality/); [Turing LICENCE](https://github.com/TuringLang/Turing.jl/blob/HEAD/LICENCE)
- **Gen.jl** (v0.4.9, Apache 2.0): `{address} ~ distribution(args...)` records a random choice at an address in a trace; a choice map sends addresses to values for one execution; trace translators are the building blocks of inference across model representations, involutive MCMC among them — [Gen bottom-up introduction](https://www.gen.dev/tutorials/bottom-up-intro/tutorial); [Gen trace translators](https://www.gen.dev/docs/stable/ref/inference/trace_translators/); [Gen.jl LICENSE](https://github.com/probcomp/Gen.jl/blob/HEAD/LICENSE)
- **PRISM** (v4.11, GPL version 2 **[copyleft]**): a model is modules of guarded commands with probabilistic updates. Verbatim: `mdp` / `module M1` / `x : [0..2] init 0;` / `[] x=0 -> 0.8:(x'=0) + 0.2:(x'=1);` / `[] x=1 & y!=2 -> (x'=2);`. Model types: `dtmc`, `ctmc`, `mdp`, `pta`, `pomdp`, `popta`; with no keyword an MDP is assumed — [PRISM language example](https://www.prismmodelchecker.org/manual/ThePRISMLanguage/Example1); [PRISM model types](https://www.prismmodelchecker.org/manual/ThePRISMLanguage/ModelType); [prism COPYING.txt](https://github.com/prismmodelchecker/prism/blob/HEAD/COPYING.txt)
- **Storm** (2.0.0 of October 2026, "a major release with numerous breaking changes"; GPL version 3 **[copyleft]**) reads "(almost) the full PRISM language" extended to Markov automata, JANI, generalised stochastic Petri nets (PNML or GreatSPN files), dynamic fault trees, and explicit formats — [Storm input languages](https://www.stormchecker.org/documentation/background/languages.html); [storm CHANGELOG](https://github.com/moves-rwth/storm/blob/HEAD/CHANGELOG.md); [storm LICENSE](https://github.com/moves-rwth/storm/blob/HEAD/LICENSE)
- **DifferentialEquations.jl:** an SDE is a pair of functions f and g; non-diagonal noise is declared by the keyword `noise_rate_prototype` of `SDEProblem`, a prototype of the matrix g writes. The interpretation is a property of the solver: `EM` is Itô and `EulerHeun` its Stratonovich counterpart; `RKMil(interpretation=:Stratonovich)` switches a method; `LambaEM` and `LambaEulerHeun` are the adaptive pair for the two interpretations. StochasticDiffEq.jl is at v6.100.0, MIT — [DiffEq SDE solvers](https://docs.sciml.ai/DiffEqDocs/dev/solvers/sde_solve/); [StochasticDiffEq.jl releases](https://github.com/SciML/StochasticDiffEq.jl/releases/latest)
- **Brian 2:** the documentation states the interpretation only for the `heun` method (Stratonovich); the equations page, where `xi` is declared, does not say which interpretation an equation has — [Brian 2 numerical integration](https://brian2.readthedocs.io/en/stable/user/numerical_integration.html); [Brian 2 equations](https://brian2.readthedocs.io/en/stable/user/equations.html)
- **XPPAUT:** `wiener` variables scale as sqrt(dt); `markov` variables take a matrix of rates; the reference states no interpretation — [XPP ODE file reference](https://sites.pitt.edu/~phase/bard/bardware/xpp/help/xppodes.html)
- **Catalyst:** noise comes either from the reaction network's own semantics (chemical Langevin SDE, jump process) or from declared `@brownians` and `@poissonians` coupled to equations — [Catalyst docs](https://docs.sciml.ai/Catalyst/stable/)
- **SBML `distrib`** and Antimony's `normal(...)`, `uniform(...)`, `poisson(...)` state that a value is sampled from a distribution; this is a draw, not a noise process in an equation — [SBML specifications](https://sbml.org/documents/specifications/); [Antimony reference](https://tellurium.readthedocs.io/en/latest/antimony.html)

### Inferences
- No surveyed language makes the interpretation of a stochastic integral part of the model's text. Since Itô and Stratonovich readings of the same expression are different processes when noise is multiplicative, a language that keeps the model apart from the method must state the interpretation in the model (or state the noise as a generator or a Fokker–Planck operator, where the question does not arise).
- The probabilistic languages and the dynamical ones do not meet: Stan and Turing treat a differential equation as an opaque deterministic function inside a model of static random variables, and the dynamical languages have no way to say that a parameter or an initial condition is a random variable with a stated law (Antimony's distribution functions and SBML `distrib` are the partial exception, without inference). A declaration `x ~ D` that may stand for a parameter, an initial value, a noise increment or a jump mark would join them.
- Gen's addressed choices and PRISM's guarded commands are the two cleanest declarations of discrete randomness: one names each choice so that it can be constrained or proposed, the other attaches probabilities (or rates, for a CTMC) to transitions. A jump process with marks needs both: a rate on the transition and a named law for the mark.

### Gaps
- Whether Stan has any SDE facility (it does not, to prior knowledge) is unconfirmed: the pages read do not mention SDEs at all, and Stan's known restriction to continuous parameters was not on the pages read.
- Whether `SDEProblem` or ModelingToolkit's `SDESystem` carries any declaration of interpretation in the model was not found; the documentation read places it in the solver.
- Brian 2's interpretation for `euler` and `milstein` is not stated on the page read.
- ModelingToolkit's own syntax for Brownian variables (`@brownians` in MTK itself) and its noise-equation form were not on the pages read.
- PRISM-games' `smg`/`csg` types and Storm's POMDP support were not on the pages read.

## 4. Rule-Based and Generative Systems: Whether a Grammar Can Be Written as a Dynamical System

### Takeaway
Yes, in a restricted sense: BNGL and Kappa are graph-rewriting languages with rates whose semantics is a continuous-time Markov chain, and L-systems are parallel string rewriting in discrete time. Graph-transformation tools (GROOVE) give rules a transition-system semantics with no time or probability. Only Mjolsness's dynamical grammars set out to put rewriting rules, rates and differential equations in one formalism with one operator-algebra semantics, and they have no maintained, general implementation found here.

### Cited Findings
- **BioNetGen (BNGL):** a model is blocks (parameters, molecule types, species, observables, reaction rules) followed by actions. The quickstart's SIR model has species `S()` and `I()`, observables `Molecules S S()`, rules `R1: S + I -> I + I b` and `R2: I -> R g`, and the actions `generate_network({overwrite=>1})` and `simulate({method=>"ode",t_end=>30,n_steps=>200})` — [BioNetGen quickstart](https://bionetgen.readthedocs.io/en/latest/bng_quickstart.html)
- BNGL molecules have components with states and bonds: molecule type `A(c0~R~S, c0~R~S)`; a rule that binds and changes state, `A(c0~R) + B(c2) -> A(c0~S!1).B(c2!1) rate`; "a reaction rule defines a graph transformation" that creates or removes bonds, changes states, or adds or removes molecules — [BNGL support in MCell4](https://mcell.org/mcell4_documentation/bngl.html)
- One BNGL model is simulated three ways: as a generated network (ODE, SSA, PLA), or network-free in NFsim, or as a hybrid particle/population model — [BioNetGen 2.2 paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC5079481)
- BioNetGen 2.9.3, MIT; PyBioNetGen 0.8.7 (2026-09-04) — [bionetgen releases](https://github.com/RuleWorld/bionetgen/releases/latest); [bionetgen LICENSE](https://github.com/RuleWorld/bionetgen/blob/HEAD/LICENSE); [bionetgen on PyPI](https://pypi.org/project/bionetgen/)
- **Kappa (KaSim 4):** agents are declared with sites and internal states, `%agent: C(x1{u p},x2{u p})` (`{}` internal states, `[]` link states); a reversible binding rule in KaSim 4 syntax is `A(x[.]),B(x[.]) <-> A(x[1]),B(x[1]) @ on_rate, off_rate`; rates may be binary with an optional unary rate in braces; `%var:`, `%init:`, `%obs:` declare variables, initial mixtures and observables — [KaSim manual](https://tools.kappalanguage.org/docs/KaSim-manual-master/KaSim_manual.htm); [kappa-agents changes](https://ocaml.org/p/kappa-agents/4.1.3/doc/CHANGES.html)
- Kappa "interventions" (`%mod:`) are condition–action statements on the running simulation: a precondition, `do`, modifications (`$ADD`, `$SNAPSHOT`, `$PRINT`), and `repeat` with a condition, e.g. `%mod: |A(a)| < 100 do $SNAPSHOT ...`; tokens (continuous quantities) are initialised by `%init: [alg_expr] [token_name]` — [kappa-agents changes](https://ocaml.org/p/kappa-agents/4.1.3/doc/CHANGES.html)
- Kappa's simulator picks a rule with probability proportional to its activity (the number of matches of its left side times its rate) over the sum of all activities, the pace being "governed by mass action dynamics" — [The Kappa tutorial, v4.1](https://kasim.readthedocs.io/en/stable/tutorial.html)
- KappaTools (KaSim, a stochastic simulator; KaSa, a static analyser; Kappy, a Python client) is at v4.1.3.1 under LGPL 3.0 **[weak copyleft]** — [KappaTools](https://github.com/Kappa-Dev/KappaTools); [KappaTools releases](https://github.com/Kappa-Dev/KappaTools/releases/latest)
- **L-Py:** L-system constructs "were added to the syntax of Python", following cpfg and L+C as closely as possible, without type declarations; an L-Py file mixes Python code and L-system rules and is first translated into pure Python (Boudon, Pradal, Cokelaer, Prusinkiewicz, Godin, Frontiers in Plant Science 2012) — [L-Py paper](https://www.frontiersin.org/articles/10.3389/fpls.2012.00076/text)
- L-Py v3.15.4, released under "a CeCILL license, which is compatible to the GNU GPL" **[copyleft]** — [openalea/lpy](https://github.com/openalea/lpy); [lpy releases](https://github.com/openalea/lpy/releases/latest)
- **GROOVE:** systems are modelled as graphs and transformation rules, applied interactively or exhaustively; a grammar is a directory `.gps` with rules (`.gpr`), host graphs (`.gst`) and type graphs (`.gty`) serialised in GXL (XML); rules are drawn as a single graph in which creator (`++`), eraser (`-`) and embargo (`!`) elements are marked; features: negative application conditions, universally quantified (nested) rules, data attributes, type graphs, a control language with sequencing, choice, loops and recipes; exploration yields a graph transition system with isomorphic states collapsed, checked against CTL or LTL. Version 7.6.0 in the manual (release tag 7.6.1), Java 21, Apache 2.0 — [GROOVE manual, introduction](https://groove.cs.utwente.nl/manual_introduction.html); [GROOVE manual, storage formats](https://groove.cs.utwente.nl/manual_io.html); [GROOVE releases](https://github.com/nl-utwente-groove/code/releases/latest)
- GROOVE's introduction mentions no stochastic or timed semantics — [GROOVE manual, introduction](https://groove.cs.utwente.nl/manual_introduction.html)
- **Petri nets (PNML):** ISO/IEC 15909-2 (2009, revised 2011) defines the transfer format PNML for Place/Transition nets, high-level Petri net graphs and symmetric nets, around a core model to which new net types can be added — [PNML and ISO/IEC 15909-2](https://www.pnml.org/papers/PNML-EKA06.V3.pdf); [A primer on PNML](https://orbit.dtu.dk/en/publications/a-primer-on-the-petri-net-markup-language-and-isoiec-15909-2/)
- Generalised stochastic Petri nets are read by Storm from PNML or GreatSPN project files — [Storm input languages](https://www.stormchecker.org/documentation/background/languages.html)
- **Dynamical grammars** (Mjolsness and Yosiphon, "Stochastic Process Semantics for Dynamical Grammars", Annals of Mathematics and Artificial Intelligence 2007, DOI 10.1007/s10472-006-9034-1, arXiv:cs/0511073): rules map multisets of typed, parameterised terms to terms with a rate clause, e.g. `{bacterium(x), macrophage(y)} → macrophage(y) with ρ(‖x−y‖)`; a `subject to` clause translates to a `with` clause by a delta function; dynamical grammars add `solving`/`solve` clauses for ODEs and SDEs, translatable into `with` clauses by derivatives of delta functions — [arXiv:cs/0511073](https://ar5iv.labs.arxiv.org/html/cs/0511073)
- The semantics maps a grammar into an algebra of operators built from creation and annihilation operators: addition for independent processes, multiplication for co-occurring events; in continuous time the master equation dPr/dt = H·Pr with Pr(t) = exp(tH)·Pr(0); a time-ordered product expansion of exp(tH) yields the Gillespie algorithm for reaction networks. The authors list as expressible: clustering models, logic programs, ODEs and SDEs (with Fokker–Planck forms), mass-action reaction networks, graph and string grammars including some L-systems, and reaction–diffusion, with a generalisation to PDEs and SPDEs mentioned. The implementation described is "a preliminary implementation of an interpreter for most of this syntax in the form of a Mathematica notebook" — [arXiv:cs/0511073](https://ar5iv.labs.arxiv.org/html/cs/0511073)
- Mjolsness's 2022 paper extends the framework to "dynamical graph grammars", with rules carrying local differential-equation dynamics for continuous parameters — [Frontiers in Systems Biology 2022](https://www.frontiersin.org/articles/10.3389/fsysb.2022.898858)

### Inferences
- A grammar is written as a dynamical system in exactly the tools that attach a rate to a rule (BNGL, Kappa, stochastic Petri nets): the state is a multiset or a site graph, and the dynamics is the continuous-time Markov chain whose generator sums the rules' operators. This is the same construction as Doi–Peliti and as the dynamical grammars' operator algebra, which gives a new language a single semantic target for reaction networks, rewriting rules and jump processes.
- The graph-transformation community's tools (GROOVE, and AGG by its reputation) and the rule-based modelling tools solve disjoint halves: GROOVE has nested quantification, typing, control and exhaustive exploration but no rates; Kappa and BNGL have rates and efficient simulation but only site graphs with flat rules. Neither rewrites a cell complex or carries continuous state on what is rewritten, except through Kappa's tokens and counters.
- L-systems are maps (parallel rewriting, discrete time); BNGL and Kappa are flows of measures (sequential rewriting, continuous time). A language that states the time model of a rule set separately (parallel synchronous, sequential with rates, or under a control program) would cover all three.
- Dynamical grammars are the nearest prior statement of the objective here, including their limit: differential equations enter as clauses of rules, not as fields over a space, and no action or quantum dynamics appears.

### Gaps
- cpfg's own input format and its licence were not researched; L-Py's rule syntax (`Axiom:`, `production:`, `A(x) --> F(x)[+A(x/2)]`, context by `<` and `>`, stochastic choice inside a rule's Python body) is from prior knowledge, since the documentation pages returned 404. L-Py's exact CeCILL variant (CeCILL-C or CeCILL 2.x) was not established.
- AGG was not researched in this session; no source is given for it.
- KaDE (ODE generation from Kappa rules) and KaStor (causal stories) are named in the request but were not on the repository page read; the Kappa manual host did not resolve at the time of writing, so the `%token:` declaration and counters are unverified.
- No current implementation of dynamical (graph) grammars was verified; from prior knowledge there are Plenum (Mathematica) and a C++ library, DGGML, neither confirmed here.
- The ISO standard's treatment of stochastic and timed nets was not found; the results suggest they are outside the standardised net types, which is an inference from its listed scope.

## 5. Actions and Field Theories: How an Action Is Written and What Is Derived from It

### Takeaway
The particle-physics tools take a Lagrangian as a symbolic expression in declared fields and derive Feynman rules, mass matrices and (SARAH) renormalisation group equations, for local, Lorentz- and gauge-invariant theories in four dimensions. Tensor algebra systems (Cadabra, xAct) vary an action to get field equations. Lattice and spin-foam codes take no declarative action at all: the action is C++ or hand-ordered index loops, and nothing found accepts a group field theory or a spin-foam model as input.

### Cited Findings
- **FeynRules** (Mathematica; arXiv:1310.1921, Computer Physics Communications 185 (2014) 2250): a model is "a list of fields, parameters and a Lagrangian". Verbatim declarations: gauge group `SU3C == { Abelian -> False, CouplingConstant -> gs, GaugeBoson -> G, StructureConstant -> f, Representations -> {{T,Colour}}, SymmetricTensor -> dSUN }`; parameter `aS == { ParameterType -> External, InteractionOrder -> {QCD, 2}, Value -> 0.1184, BlockName -> SMINPUTS, OrderBlock -> 3, ... }`; field `F[1] == { ClassName -> psi, SelfConjugate -> False, WeylComponents -> {chi, xibar} }` — [FeynRules 2.0, arXiv:1310.1921](https://ar5iv.labs.arxiv.org/html/1310.1921)
- A Lagrangian term is a Mathematica expression with explicit indices and `Dot` for fermion chains, e.g. `gs Ga[mu, s, r] T[a, i, j] dqbar[s, f, i].dq[r, f, j] G[mu, a]`; covariant derivatives are `DC[phi, mu]` — [FeynRules 2.0, arXiv:1310.1921](https://ar5iv.labs.arxiv.org/html/1310.1921)
- FeynRules derives Feynman rules "using canonical commutation relations among fields and creation operators"; supports fields of spin 0, 1/2, 1, 3/2 and 2 and superfields; extracts tree-level mass matrices (diagonalised by ASperGe); exports to CalcHep, FeynArts, MadGraph, Sherpa, Whizard and the UFO format; the Lagrangian must satisfy locality and Lorentz and gauge invariance — [FeynRules 2.0, arXiv:1310.1921](https://ar5iv.labs.arxiv.org/html/1310.1921)
- FeynRules' repository is at `fr-2.3.49` under GPL version 3 **[copyleft]**, though the 2014 paper's program summary says "Licensing provisions: None"; it also requires Mathematica (proprietary) — [FeynRules LICENSE](https://github.com/FeynRules/FeynRules/blob/HEAD/LICENSE); contradicted by [arXiv:1310.1921](https://arxiv.org/abs/1310.1921)
- **LanHEP** (Semenov; arXiv:0805.0555, version 3.1 in arXiv:1005.1909): the input is a sequence of statements, each starting with a keyword and ending with a full stop; particles declared by spin (`scalar P/aP:(options).`, `spinor`, `vector`); Lagrangian terms by `lterm`, auxiliary expressions by `let`. Verbatim QED: `let F^mu^nu=deriv^mu*A^nu-deriv^nu*A^mu.` / `lterm -1/4*(F^mu^nu)**2 - 1/2*(deriv^mu*A^mu)**2.` / `lterm E1*(i*gamma*deriv+me)*e1.` Output: Feynman rules as CompHEP model tables, FeynArts files or LaTeX — [LanHEP manual, arXiv:0805.0555](https://ar5iv.arxiv.org/html/0805.0555); [LanHEP 3.1, arXiv:1005.1909](https://ar5iv.arxiv.org/html/1005.1909); [LanHEP page](https://theory.sinp.msu.ru/~semenov/lanhep.html)
- **SARAH** (Mathematica; Staub, arXiv:1309.7223): the model file states symmetries, fields and a potential, and SARAH supplies the rest. Verbatim lines: `Global[[1]] = {Z[2], RParity};` / `Gauge[[1]]={B, U[1], hypercharge, g1, False, RpM};` / `SuperFields[[1]] = {q, 3, {uL, qL}, 1/6, 2, 3, RpM};` / `ScalarFields[[1]] = {H, 1, {H0, Hm}, 1/2, 2, 1};` / `SuperPotential = Yu u.q.Hu - Yd d.q.Hd - Ye e.l.Hd + \[Mu] Hu.Hd;` / `LagNoHC = -Mu2 conj[H].H + 1/2 \[Lambda] conj[H].H.conj[H].H;` / `DEFINITION[EWSB][VEVs]= {{H0, {v, 1/Sqrt[2]}, {Ah,I/Sqrt[2]},{hh, 1/Sqrt[2]}}};` — [SARAH 4, arXiv:1309.7223](https://ar5iv.labs.arxiv.org/html/1309.7223)
- SARAH derives: kinetic terms, gauge interactions, D-terms, gauge fixing and ghosts from the declared symmetries; mass matrices, tadpole equations, vertices; one-loop tadpoles and self-energies; one- and two-loop RGEs for supersymmetric and other models; checks of gauge anomalies; and model files for CalcHep/CompHep, FeynArts, WHIZARD, UFO, Vevacious and Fortran source for SPheno — [SARAH 4, arXiv:1309.7223](https://ar5iv.labs.arxiv.org/html/1309.7223)
- **Cadabra** ("a field-theory motivated approach to computer algebra"): input in "a subset of LaTeX notation"; handles anti-commuting and non-commuting objects, gamma matrix algebra, Fierz identities, implicit dependence of tensors on coordinates, multi-term symmetries (Bianchi) and dimension-dependent identities (Schouten); it leaves an expression unchanged unless an operation is asked for. Release 2.6.0 of 14 October 2026; GPL version 3 **[copyleft]** — [Cadabra](https://cadabra.science/); [cadabra2 LICENSE](https://github.com/kpeeters/cadabra2/blob/HEAD/LICENSE)
- **xAct** (Mathematica): `VarD[tens, cd][expr]` "takes the functional derivative of expr w.r.t the tensor tens, while integrating by parts w.r.t. the derivative cd"; xTras overrides it for variations with respect to a metric (arXiv:1308.3493); FieldsX adds fermions, gauge fields and BRST cohomology (arXiv:2008.12422); a 2026 package, xCPS, for covariant phase space and Noether charges notes that `VarD` does not take variational relations into account (arXiv:2606.05204) — [xTras tutorial](https://xact.es/xTras/documentation/tutorial/SpinTwo.html); [xTras, arXiv:1308.3493](https://arxiv.org/pdf/1308.3493); [FieldsX, arXiv:2008.12422](https://arxiv.org/pdf/2008.12422); [xCPS, arXiv:2606.05204](https://arxiv.org/pdf/2606.05204)
- **Grid** (Boyle, Cossu, Yamaguchi, Portelli, arXiv:1512.03487) is a data-parallel C++ library for lattice QCD; the paper concerns its programming patterns and performance. Hadrons is "a Grid-based workflow management system for lattice field theory simulations". Grid is GPL version 2 **[copyleft]**; its "latest release" tag dates from a 2020 workaround, i.e. it is used from the repository head — [Grid, arXiv:1512.03487](https://arxiv.org/abs/1512.03487v1); [Hadrons](https://github.com/aportelli/Hadrons); [Grid LICENSE](https://github.com/paboyle/Grid/blob/HEAD/LICENSE); [Grid releases](https://github.com/paboyle/Grid/releases/latest)
- **sl2cfoam-next** (Gozzini, arXiv:2107.13952; how-to in arXiv:2202.04360) computes Lorentzian EPRL spin-foam vertex amplitudes. The user initialises with the Immirzi parameter (`SL2Cfoam.cinit(...)`), gives ten boundary spins and a cut-off (`vertex_compute(spins, Dl)`), and receives a five-index tensor over boundary intertwiners. The 2-complex is not data: an amplitude over several vertices is assembled by hand in nested loops over intertwiners; the vertex is defined only for 4-simplices; sums over spins need a cut-off with no known rule for choosing it. GPL version 3 **[copyleft]**; no tagged releases — [How-to compute EPRL spin foam amplitudes, arXiv:2202.04360](https://ar5iv.labs.arxiv.org/html/2202.04360); [arXiv:2107.13952](https://arxiv.org/abs/2107.13952); [sl2cfoam-next COPYING](https://github.com/qg-cpt-marseille/sl2cfoam-next/blob/HEAD/COPYING)
- A search for software or an input language specific to group field theory or tensor models returned only general Feynman-amplitude tools (FeynCalc, FeAmGen.jl, AmpRed, a small Python package `feynamp`), none of them for group field theory — [search result: feynamp](https://pypi.org/project/feynamp)

### Inferences
- The Lagrangian tools derive a great deal (vertices, masses, RGEs, anomaly checks) because they restrict the class of theories sharply: fields on Minkowski space, classified by spin and gauge representation, local polynomial interactions. Their derivations are the perturbative expansion about a free theory. None derives classical Euler–Lagrange equations of motion as a dynamical system to be integrated; that is done by Cadabra and xAct, which in turn produce no simulation.
- SARAH's economy is instructive: the user states the symmetries and the non-gauge potential, and everything fixed by gauge invariance is generated. A language in which a symmetry is declared and its consequences derived (conserved currents, admissible terms) follows this pattern.
- Between "action in, Feynman rules out" and "C++ in, configurations out" there is no declarative middle: no surveyed format states a lattice action over a complex, a group field theory's kernels and interaction pattern, or a spin-foam model's vertex and face amplitudes as data from which the expansion, the amplitudes or a Monte Carlo update are derived. This is the clearest unoccupied ground in the survey.
- Every tool in this group except Grid's own code depends on Mathematica or is GPL; none is MIT-compatible for reuse of code, though formats and ideas can be studied freely.

### Gaps
- No licence statement was found for SARAH or LanHEP, nor a current version number for either as of November 2026 (LanHEP's page lists 3.0.0 of May 2008 with a 3.1 manual of 2010; whether it is maintained is unknown). LanHEP's UFO export is unconfirmed.
- xAct's licence and current version were not found (from prior knowledge, GPL; unverified).
- Cadabra's syntax for properties (`A_{m n}::AntiSymmetric.`) and for varying an action (`vary`, `integrate_by_parts`) is from prior knowledge; the front page shows no example.
- The formats of lattice codes' parameter files (Grid's and Hadrons' XML applications, Chroma's XML, openQCD's input files) were not retrieved; the statement that the action is chosen by name with numerical parameters, never written symbolically, is from prior knowledge.
- No source was found, positive or negative, on a textual language for group field theories; the absence is a search result, not a published statement.
- Classical-mechanics tools that derive Euler–Lagrange equations from a Lagrangian (SymPy's `LagrangesMethod`, variational-integrator codes) were outside what was fetched.

## 6. Open Quantum Systems: How a Hamiltonian and Collapse Operators Are Stated

### Takeaway
Every surveyed package states an open quantum system as host-language objects, a Hamiltonian operator and a list of collapse (jump) operators with rates, passed to a solver function; none has a textual model language. The only symbolic layer found is QuantumCumulants.jl, which derives mean-field equations from H and the jumps and hands them to ModelingToolkit.

### Cited Findings
- **QuTiP** (v5.3.1, PyPI 2026-08-04; BSD three-clause-style licence): `mesolve(H, psi0, times, [np.sqrt(0.05) * sigmax()], e_ops=[sigmaz(), sigmay()])` with `H = 2*np.pi * 0.1 * sigmax()`; "a list of collapse operators (c_ops) is passed as the fourth argument", each the square root of a rate times an operator — [QuTiP master equation guide](https://qutip.readthedocs.io/en/latest/guide/dynamics/dynamics-master.html); [qutip on PyPI](https://pypi.org/project/qutip/); [qutip LICENSE.txt](https://github.com/qutip/qutip/blob/HEAD/LICENSE.txt)
- Time dependence in QuTiP 5 is a `QobjEvo`, built from a function, from a list `[H0, [H1, coeff]]`, or from an operator times a coefficient; a coefficient is a Python function `f(t, ...)`, an array interpolated by splines, or a string, "a simple Python expression" such as `"A * exp(-(t / sigma)**2)"` with `args`, which may be compiled by Cython — [QuTiP time-dependent guide](https://qutip.readthedocs.io/en/latest/guide/dynamics/dynamics-time.html)
- **QuantumOptics.jl** (v1.2.10, MIT): `timeevolution.master(tspan, rho0, H, J; rates=...)`; variants `master_h`, `master_nh` (non-Hermitian effective Hamiltonian), `master_dynamic`, `master_nh_dynamic`; separate functions for stochastic Schrödinger and master equations and for semiclassical systems — [QuantumOptics.jl master equation](https://docs.qojulia.org/timeevolution/master/); [QuantumOptics.jl LICENSE.md](https://github.com/qojulia/QuantumOptics.jl/blob/HEAD/LICENSE.md)
- **QuantumToolbox.jl** (v0.51.1, BSD three-clause, in the QuTiP organisation): `mesolve` with `c_ops` a list whose elements are each a `Qobj` or a `QobjEvo`; `QuantumObjectEvolution` (`QobjEvo`) represents time-dependent operators on SciMLOperators.jl — [QuantumToolbox.jl mesolve](https://qutip.org/QuantumToolbox.jl/stable/users_guide/time_evolution/mesolve); [QuantumToolbox.jl time dependence](https://qutip.org/QuantumToolbox.jl/stable/users_guide/time_evolution/time_dependent); [QuantumToolbox.jl LICENSE](https://github.com/qutip/QuantumToolbox.jl/blob/HEAD/LICENSE)
- **QuantumCumulants.jl** (v0.7.2, MIT) is symbolic. Verbatim: `h_cav = FockSpace(:cavity)` / `h_atom = NLevelSpace(:atom, (:g,:e))` / `h = tensor(h_cav, h_atom)` / `@qnumbers a::Destroy(h)` / `σ(i, j) = Transition(h, :σ, i, j)` / `H = Δ*a'*a + g*(a'*σ(:g,:e) + a*σ(:e,:g))` / `J = [a,σ(:g,:e),σ(:e,:g)]` / `rates = [κ,γ,ν]` / `eqs = meanfield([a,σ(:g,:e),σ(:e,:e)], H, J; rates=rates, order=1)`. It derives equations of motion for averages from the commutation relations, truncates them by a cumulant expansion at a stated order, and converts them to a ModelingToolkit `System`; its operator algebra is SecondQuantizedAlgebra.jl — [QuantumCumulants.jl](https://qojulia.github.io/QuantumCumulants.jl/stable/); [QuantumCumulants.jl LICENSE.md](https://github.com/qojulia/QuantumCumulants.jl/blob/HEAD/LICENSE.md)
- XPPAUT-like or SBML-like text formats for quantum dynamics: none was found on any page read; QuTiP's guide mentions no text-file model format — [QuTiP master equation guide](https://qutip.readthedocs.io/en/latest/guide/dynamics/dynamics-master.html)

### Inferences
- The data of a Markovian open quantum system is small and uniform across packages: a Hilbert space (a tensor product of named factors), H, a list of pairs (rate, jump operator), an initial state and observables. A textual notation for it is straightforward and is absent only because the packages are libraries.
- QuTiP and QuantumOptics.jl hold operators as matrices, so nothing symbolic survives (no commutators, no derived equations); QuantumCumulants.jl holds them as symbols with commutation relations and can therefore derive the dynamics of moments. This is the same split as opaque right-hand sides against symbolic equations in the classical languages, and the symbolic side is again what makes derivation possible.
- The parallel with classical stochastic systems is exact enough to share notation: collapse operators with rates are to the Lindblad generator what reactions with rates are to a master equation's generator, and unravellings (quantum jumps, diffusive) correspond to the choice between a jump process and an SDE. No package states that correspondence in its interface.

### Gaps
- QuTiP's other solvers (`mcsolve`, `ssesolve`, `smesolve`, `brmesolve`, HEOM) and how measurement operators for stochastic unravellings are declared were not on the pages read.
- Whether any textual DSL exists for open quantum systems (for instance in pulse-level or quantum-optics packages not surveyed) is unknown; none was found, and the search was not exhaustive.
- Non-Markovian descriptions (memory kernels, bath spectral densities) were not researched.

## 7. Categorical and Compositional Approaches: What They Contribute to Composition

### Takeaway
AlgebraicJulia separates the pattern of composition (a wiring diagram, a morphism of an operad) from the systems composed (an algebra of that operad), so that one diagram composes ODEs, discrete maps or delay systems alike, and distinguishes sharing a resource from feeding an output to an input. Its primitive systems are opaque Julia functions; Decapodes adds a symbolic, typed language of discrete exterior calculus on top, composed by the same diagrams.

### Cited Findings
- **AlgebraicDynamics.jl** (v0.2.2, MIT) is "a Julia library for compositional dynamical systems" on Catlab.jl: "The implementation of the composition of dynamical systems follows the mathematics of operads and operad algebras." Three syntaxes: undirected wiring diagrams with resource sharers (`ContinuousResourceSharer{T}`, `DiscreteResourceSharer{T}`), directed wiring diagrams with machines (`ContinuousMachine{T}`, `DiscreteMachine{T}`), and open circular port graphs; continuous machines and sharers can be solved as delay problems (`DDEProblem`) — [AlgebraicDynamics.jl](https://algebraicjulia.github.io/AlgebraicDynamics.jl/dev/); [AlgebraicDynamics.jl LICENSE](https://github.com/AlgebraicJulia/AlgebraicDynamics.jl/blob/HEAD/LICENSE)
- Its references: Schultz, Spivak et al., arXiv:1609.08086 (directed composition of continuous systems); Vagner et al., arXiv:1408.1598 (directed composition of discrete systems); Baez and Pollard, arXiv:1704.02051 (undirected composition); Libkind, arXiv:2007.14442 (overview) — [AlgebraicDynamics.jl](https://algebraicjulia.github.io/AlgebraicDynamics.jl/dev/)
- Verbatim Lotka–Volterra by resource sharing: `rf = @relation (rabbits,foxes) begin growth(rabbits); predation(rabbits,foxes); decline(foxes) end` / `dotr(u,p,t) = p.α*u` / `dotrf(u,p,t) = [-p.β*u[1]*u[2], p.γ*u[1]*u[2]]` / `dotf(u,p,t) = -p.δ*u` / `rabbit_growth = ContinuousResourceSharer{Float64}(1, dotr)` / `rabbitfox_system = oapply(rf, [rabbit_growth, rabbitfox_predation, fox_decline])` / `prob = ODEProblem(rabbitfox_system, u0, tspan, params)`; the dynamics are plain Julia functions `(u,p,t)` — [AlgebraicDynamics.jl Lotka–Volterra example](https://algebraicjulia.github.io/AlgebraicDynamics.jl/dev/examples/Lotka-Volterra/)
- **Decapodes.jl** (v0.6.9, MIT) is "a framework for developing, composing, and simulating physical systems", combining applied category theory (for formalising and composing equations) with the discrete exterior calculus (for differential operators); CombinatorialSpaces.jl supplies simplicial complexes and their operators, DiagrammaticEquations.jl the equations as diagrams; the stated benefits are hierarchical composition, generality over manifolds and a human-readable DSL; the documentation says the library is under active development and "a stable API/behavior cannot yet be assumed" — [Decapodes.jl](https://algebraicjulia.github.io/Decapodes.jl/dev/); [Decapodes.jl LICENSE](https://github.com/AlgebraicJulia/Decapodes.jl/blob/HEAD/LICENSE)
- In a `@decapode` block variables are "typed by the dimension and orientation of the information they contain" (`C::Form0` on vertices, `Form1` on edges, `Form2` on triangles, `k::Constant`), and equations use `∂ₜ`, `d₀`, `⋆₁`, `dual_d₁`. Composition: `@relation (C, V) begin diffusion(C, ϕ₁) ... end`, then `oapply(compose_diff_adv, [Open(Diffusion, [:C, :ϕ]), ...])` and `apex(...)` of the resulting cospan. Simulation: a dual mesh (`EmbeddedDeltaDualComplex2D`, `subdivide_duals!`), `sim = eval(gensim(Diffusion))`, `fₘ = sim(dualmesh, nothing, DiagonalHodge())`, then an `ODEProblem`; the tooling "will automatically generate an explicit method for solving the system" — [Decapodes.jl overview](https://algebraicjulia.github.io/Decapodes.jl/dev/overview/overview/)
- **Catlab.jl** (v0.17.6, MIT) is the base library; AlgebraicPetri.jl (v0.10.0, MIT) builds Petri-net models on it — [Catlab.jl releases](https://github.com/AlgebraicJulia/Catlab.jl/releases/latest); [AlgebraicPetri.jl releases](https://github.com/AlgebraicJulia/AlgebraicPetri.jl/releases/latest)
- Other composition mechanisms in the survey, for comparison: Modelica and ModelingToolkit compose acausally through connectors ("components, a lazy connection system, and expansion/flattening") — [MTK docs](https://docs.sciml.ai/ModelingToolkit/stable/); Antimony instantiates modules with interface symbols and identifies symbols by `is` — [Antimony reference](https://tellurium.readthedocs.io/en/latest/antimony.html); Catalyst uses `compose` and `extend` — [Catalyst docs](https://docs.sciml.ai/Catalyst/stable/); SpaceEx and CIF synchronise automata on shared labels — [ECC 2013 paper on SpaceEx models](https://skoge.folk.ntnu.no/prost/proceedings/ecc-2013/data/papers/1270.pdf); LEMS composes hierarchically by child components — [LEMS in the NeuroML documentation](https://docs.neuroml.org/Userdocs/LEMS.html)

### Inferences
- The contribution is a stated semantics of composition: the composite of systems along a diagram is defined by functoriality, so that composing in stages equals composing at once, and the same diagram applies to any kind of system for which an algebra is given. The equation-based languages get composition from flattening (Modelica, ModelingToolkit, Antimony) and state no such law.
- Two kinds of interface are distinguished that other languages blur: an undirected junction at which systems share a quantity and their contributions add (resource sharing, Baez–Pollard), and a directed wire from an output to an input (machines). Modelica's flow and potential variables in connectors encode the first; signal blocks the second.
- AlgebraicDynamics composes opaque functions, so nothing can be derived from the composite (no Jacobian, no conservation law, no units). Decapodes shows the remedy: keep the equations symbolic and typed, compose the syntax, and compile afterwards. Decapodes' types (primal and dual forms of each degree) are also the surveyed precedent for typing a field by where it lives on a complex.
- The approach has not been extended, in what was read, to stochastic, hybrid, quantum or action-based systems; its Petri nets (AlgebraicPetri) cover mass-action reaction networks.

### Gaps
- The reference papers for Decapodes (from prior knowledge: Patterson, Baas, Hosgood, Fairbanks, "A diagrammatic view of differential equations in physics", arXiv:2204.01843, and a later Decapodes paper) were not confirmed from the pages read.
- Decapodes' type inference and resolution of overloaded operators are not described on the pages read.
- Whether AlgebraicDynamics has stochastic or hybrid system types, and whether structured-cospan or double-categorical libraries (from prior knowledge, later AlgebraicJulia work) now supersede it, was not established; its low version number (0.2.2) suggests slow development, which is an inference.
- Catlab's own contribution (generalised algebraic theories, C-sets, wiring diagrams as data) was not read from its documentation in this session.

## 8. Recurring Design Lessons, and What No Existing Language Expresses Together

### Takeaway
Four lessons recur: keep the model apart from the numerical method; keep equations as symbolic data so that Jacobians, simplifications and other equations can be derived; carry physical dimensions in the declaration of every quantity; and treat events as first-class, with an explicit rule for simultaneity. No language surveyed states together a flow or map, typed hybrid events, noise with a stated law and interpretation, a Lindblad generator, an action, and a rate-carrying rewriting rule; the nearest partial unions are ModelingToolkit with Catalyst (classical dynamics of every kind, symbolic) and dynamical grammars (rules with rates and differential equations under one operator semantics).

### Cited Findings

**The lessons, each with its evidence**
- *Model apart from method.* Brian 2 chooses the integrator by a `method` keyword outside the equations, or automatically — [Brian 2 numerical integration](https://brian2.readthedocs.io/en/stable/user/numerical_integration.html). One Catalyst `ReactionSystem` gives ODE, SDE, jump and hybrid simulations — [Catalyst docs](https://docs.sciml.ai/Catalyst/stable/). One BNGL model runs as ODE, SSA or network-free — [BioNetGen 2.2 paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC5079481). Counter-examples: Dedalus's equation form encodes its implicit–explicit time stepping — [Dedalus tutorial 3](https://dedalus-project.readthedocs.io/en/latest/notebooks/dedalus_tutorial_3.html); NESTML's `update` block calls `integrate_odes()` imperatively — [izhikevich_neuron.nestml](https://github.com/nest/nestml/blob/master/models/neurons/izhikevich_neuron.nestml); the interpretation of an SDE is a solver option in DifferentialEquations.jl — [DiffEq SDE solvers](https://docs.sciml.ai/DiffEqDocs/dev/solvers/sde_solve/)
- *Symbolic intermediate representation.* ModelingToolkit performs index reduction, alias elimination and tearing on symbolic equations with the full Symbolics.jl system — [MTK docs](https://docs.sciml.ai/ModelingToolkit/stable/). UFL derives Jacobians and adjoints of forms — [UFL form language](https://fenics.readthedocs.io/projects/ufl/en/latest/manual/form_language.html). FeynRules and SARAH derive vertices and RGEs from a Lagrangian — [arXiv:1310.1921](https://ar5iv.labs.arxiv.org/html/1310.1921); [arXiv:1309.7223](https://ar5iv.labs.arxiv.org/html/1309.7223). QuantumCumulants derives moment equations from H and jump operators — [QuantumCumulants.jl](https://qojulia.github.io/QuantumCumulants.jl/stable/). Where the right-hand side is opaque code (Stan's ODE functions, AlgebraicDynamics's sharers, QuTiP's matrices) nothing is derived beyond numerical sensitivities — [Stan user's guide, ODEs](https://mc-stan.org/docs/stan-users-guide/odes.html); [AlgebraicDynamics.jl Lotka–Volterra example](https://algebraicjulia.github.io/AlgebraicDynamics.jl/dev/examples/Lotka-Volterra/)
- *Units.* Brian 2 requires a unit on every equation and checks it — [Brian 2 equations](https://brian2.readthedocs.io/en/stable/user/equations.html); NESTML types every quantity by a unit — [izhikevich_neuron.nestml](https://github.com/nest/nestml/blob/master/models/neurons/izhikevich_neuron.nestml); LEMS declares dimensions — [LEMS in the NeuroML documentation](https://docs.neuroml.org/Userdocs/LEMS.html); ModelingToolkit validates without converting — [MTK unit validation](https://docs.sciml.ai/ModelingToolkit/stable/basics/Validation/); Antimony's are annotations only — [Antimony reference](https://tellurium.readthedocs.io/en/latest/antimony.html)
- *Events.* Root-found state events against scheduled time events, the value before the event (`pre`, `Pre`), and priority among simultaneous events are spelled out by Modelica, ModelingToolkit and Antimony — [Modelica specification, ch. 8](https://specification.modelica.org/master/equations.html); [MTK events](https://docs.sciml.ai/ModelingToolkit/stable/basics/Events/); [Antimony reference](https://tellurium.readthedocs.io/en/latest/antimony.html)
- *Translation between formats is a recurring cost.* HyST exists because hybrid model checkers share semantics but not languages — [HyST record](https://research-explorer.ista.ac.at/record/1690); JANI exists to spare tools from parsing each other's languages and is not meant to be written by hand — [Momba: JANI meets Python](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC7984561/); ModelingToolkit imports SBML, CellML and BioNetGen — [MTK docs](https://docs.sciml.ai/ModelingToolkit/stable/)

**Criticisms and limits stated by the sources themselves**
- Antimony: a later definition silently replaces an earlier one; units do not affect the mathematics — [Antimony reference](https://tellurium.readthedocs.io/en/latest/antimony.html)
- ModelingToolkit: units are not converted; an event cannot change both variables and parameters; imperative affects are experimental — [MTK unit validation](https://docs.sciml.ai/ModelingToolkit/stable/basics/Validation/); [MTK events](https://docs.sciml.ai/ModelingToolkit/stable/basics/Events/)
- Modelica: simultaneity of events is not guaranteed and must be modelled; handling of time events is a quality-of-implementation matter — [Modelica specification, ch. 8](https://specification.modelica.org/master/equations.html)
- Decapodes: no stable API or behaviour can yet be assumed — [Decapodes.jl](https://algebraicjulia.github.io/Decapodes.jl/dev/)
- JANI: not designed to be written by a person — [Momba: JANI meets Python](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC7984561/)
- sl2cfoam-next: amplitudes beyond one vertex are assembled by hand; cut-offs have no known rule — [arXiv:2202.04360](https://ar5iv.labs.arxiv.org/html/2202.04360)
- xAct's `VarD` ignores variational relations — [xCPS, arXiv:2606.05204](https://arxiv.org/pdf/2606.05204)
- Brian 2: automatic choice of method can be slow, since trying exact integration may take considerable time — [Brian 2 numerical integration](https://brian2.readthedocs.io/en/stable/user/numerical_integration.html)

### Inferences
- **What is not expressed together.** Reading the table by columns: (a) no language has both an action and a time evolution to be integrated; the Lagrangian tools stop at Feynman rules or field equations. (b) No language has both rewriting rules and continuous fields over what is rewritten, apart from dynamical grammars on paper and Kappa's tokens. (c) No language has both a quantum generator and a classical one in the same notation, though the Lindblad form and the master equation are the same kind of object. (d) No language states the law of a random variable and the interpretation of a stochastic integral in the model. (e) No hybrid format types a mode change that alters the state space. (f) Nothing declarative exists for lattice actions on a complex, group field theories or spin foams.
- **A common semantic target exists for most of the list.** Reaction networks, rate-carrying rewriting rules, jump processes, SDEs (through their generators) and Lindblad dynamics are all linear evolutions generated by a sum of operators, one per rule, reaction, noise term or jump operator; dynamical grammars and Doi–Peliti state this for the classical cases and QuantumCumulants uses the analogous algebra for the quantum one. Flows are the deterministic limit (a first-order generator). An action is the remaining outlier: it determines a generator only after a derivation (Euler–Lagrange, or a transfer matrix on a lattice), which is exactly the derivation the Lagrangian tools automate for a narrow class.
- **The four lessons imply a shape for a new language:** declarations of typed quantities with dimensions; laws stated as symbolic data (equations, generators, actions, rules) apart from any integrator; events and rules as first-class terms with stated simultaneity and time model; interpretation of noise in the model; and composition by a stated algebra (sharing against wiring) with the composite still symbolic, as Decapodes does and AlgebraicDynamics does not.
- **Licence position.** The permissive, reusable implementations are ModelingToolkit, Catalyst, Devito, BioNetGen, the AlgebraicJulia libraries, QuantumOptics/QuantumCumulants (MIT), QuTiP, QuantumToolbox, Stan (BSD), libCellML, Pyro, Gen, GROOVE (Apache). Brian 2, NESTML, Dedalus, UFL, PRISM, Storm, Cadabra, FeynRules, Grid, sl2cfoam-next, XPPAUT, SpaceEx and L-Py are copyleft and should be studied for design only, not linked or copied into MIT code. Languages and file formats as such can be read and written by an MIT implementation; the constraint is on code.
